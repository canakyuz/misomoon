1. HARD LIMITS
==================================================================================================
- Never deploy. Never write to a remote D1 database, queue, R2 bucket or KV namespace. Never call
  the real Polar API or any payment provider. Never send email. Reading remote state is allowed only
  if /prod-review asks for it and it is read-only.
- Never loosen a test to make it pass. This includes apps/docs/src/lib/coverage.test.ts, the m.js
  1,000-byte gzip limit in packages/tracker/test/m.test.ts, the index allow-list in
  packages/core/test/indexes.test.ts, and the SDK budgets in packages/sdk/test/treeshake.test.ts.
  If a limit itself is wrong, stop and ask me.
- All SQL is built in packages/core/src/queries.ts. Unique counts stay additive across shards: no
  ratio is computed per shard and averaged.
- Competitor names appear only in docs/comparison.md, the README comparison table and
  apps/landing/src/lib/alternatives.ts, each claim with a source URL and the date it was checked.
- Svelte 5 runes only. Shared dashboard state stays in apps/dashboard/src/lib/dash.svelte.ts.
- Docs ship with the code. Docs, README and commit messages follow .claude/skills/technical-writing
  and .claude/skills/unslop.
- No legacy. Nothing has launched, so remove any code, test, type, doc or config that exists only
  for old names, old formats, old clients, renamed variables or removed providers. This includes
  aliases, fallbacks for old payload fields, and tests asserting that an old name is ignored.
  Formats that external providers still send today, such as a webhook secret format, are not
  legacy.
- Don't change prices, plan limits, retention, or what a plan includes. Those live in
  packages/core/src/plans.ts and are product decisions. If you find a contradiction there, report
  it to me.

==================================================================================================
2. WHAT MUST WORK, AREA BY AREA
==================================================================================================
For each area: read the code and the doc that describes it. Check the doc against the code. Find
the tests that cover the behaviour below, and add a test for any behaviour no test covers, even when
it works. A behaviour that works but is untested is a finding.

Tracker (packages/tracker)
- m.js stays under 1,000 bytes gzipped. It sends pageviews (history and hash routing, bfcache) and
  engagement beacons, which carry engaged time, scroll depth and the view key `y`. Every part in
  src/x/ works through misomoon.x, and the Light preset is correct.
- Nothing is tracked in the overlay, under webdriver, or with misomoon_ignore. No cookies.
- overlay.js loads only from next to m.js and talks only to window.opener.

Ingest (apps/api/src/ingest.ts, usage.ts, packages/core/src/ingest.ts)
- The edge accepts beacons and drops bots and invalid ones. Geo, UA and channel are classified.
  `visitor_id` uses the daily salt. The IP is never stored.
- Queue batching works, and with no queue bound, events are written inline.
- Duplicates are ignored through `event_id`, and a replayed or partially committed batch counts
  nothing twice.
- Engagement beacons update their pageview's row. A replayed beacon adds nothing (`pings` marks).
  A beacon that arrives out of order is handled as documented, and so is a beacon whose pageview
  isn't on the shard. A visit open at 00:00 UTC continues.
- The open-session lookup always uses its index.
- The daily ingest cap never stores more than its cap, payment refs follow their rules, and the
  capped email is sent once.

Plans and limits (packages/core/src/plans.ts, apps/api/src/plans.ts, accounts.ts, control.ts)
- With PLANS=on: the Starter site limit is atomic on site create and on site move. A retention
  setting above the plan's limit is refused, and the daily cleanup deletes at the plan's limit.
- Each person gets one trial. A second team starts with no trial. A lapsed team stops counting and
  can't add sites, while payment webhooks and dashboard reads keep working.
- Monthly events per team per UTC month: one email at 80% and one at 100%, counting stops past 125%,
  and it resets with the new month or an upgrade.
- With PLANS unset (self-hosted), none of these limits apply anywhere, and the deploy bundle carries
  no PLANS or POLAR variables.

Billing (apps/api/src/billing.ts, the dashboard PlanBilling component, docs/billing.md)
- Polar webhook signatures are verified: a wrong secret, a stale timestamp and a replayed id are
  all rejected.
- Every subscription event has the documented effect. An event that arrives out of order never
  rolls state back. Checkout creates a subscription, or switches the existing one. The customer
  portal works.
- The `billing` permission is enforced. With Polar not configured, the routes refuse and the UI
  hides billing.
- Customers' own revenue webhooks (`/api/webhooks/:provider/:site`) stay separate and keep working.

Sharding (apps/api/src/control.ts, moves.ts, scripts/deploy.ts, packages/core/src/shard.ts)
- Placement uses weighted rendezvous hashing. `shard_map` ranges route by site and by day.
- A draining shard closes its range at the right day boundary.
- Moves are resumable: copy, switch, then delete after two cache lifetimes. A retiring shard
  unbinds only when it's empty.
- Data regions keep each site on its region's shards.
- Purges are chunked, and a deleted site keeps nothing.
- Every read fans out across shard ranges and merges correctly, including the folded engagement
  columns.

Queries and the API (packages/core/src/queries.ts, apps/api/src/stats.ts, index.ts, tools.ts)
- Every stats endpoint, Stats API v2, export, journeys, funnels, behaviour reports, imported
  history, Search Console, shared links, reports, alerts and annotations returns the same numbers
  through the dashboard, the API and MCP.
- Timezones and DST buckets, the filter grammar and its limits, `compare`, and the rate limits all
  work.
- Every route checks permissions through `authorize`. Roles behave as the table in ARCHITECTURE.md
  says. Guests, API keys and shared-link tokens are scoped correctly.

SDK and plugins (packages/sdk, plugins/wordpress)
- The web, React, Next.js, React Native and Node clients send what the server accepts (the
  contract tests). They send `y` where needed, and the SDK budgets hold.
- WordPress plugin settings and hooks match docs/wordpress.md.

Dashboard (apps/dashboard)
- Every view handles its loading, empty, error and limit states.
- The Plan card, banners, PlanBilling, InstallCheck, the first-visit flow and the retention picker
  behave as documented.
- No dead UI, and no copy that contradicts the docs.

Schema and deploy (apps/api/migrations, scripts/bundle.ts, deploy.ts)
- Migrations are fresh and split by domain, because nothing has launched. Each table and its indexes
  live in the one file for their domain:
  - control: accounts, sites, shards, ingest, goals, reports, imports, payments, and billing if it
    has tables;
  - shard: events, sessions, imported.
  There are no patch files, no ALTER TABLE, and nothing that exists only to move old data. If a
  table is in the wrong file, move it, then prove the final schema is unchanged by diffing
  `sqlite_schema` before and after in node:sqlite.
- The control and shard migrations apply cleanly to an empty database.
- Every query's index use is intended.
- `pnpm bundle` produces a self-contained deploy/ that works for the Deploy to Cloudflare button.

Legal pages (docs/dpa.md, privacy.md, terms.md, security.md, compliance.md, SECURITY.md)

3. HOW TO RUN THE AUDIT
==================================================================================================
1. /prod-review with the target "everything". There is no live production, so every file is in
   scope. Build its coverage ledger over every source file in apps/, packages/, plugins/ and the
   scripts, plus every doc in docs/, and mark each one reviewed.
2. Use /haiku for the sweeps. Split the work by the areas in section 2, and give each Haiku brief
   the files, the expected behaviour above and the AGENTS.md rules. Verify every finding yourself,
   line by line, before treating it as real. Drop false positives and record why.
3. For every confirmed bug, use /test-task. Write a test with exact expected values, prove it fails
   for the right reason, fix it, run the package's tests, then commit.
4. Code quality, after the bugs:
   - Find dead code, unused exports, duplicate helpers, leftover comments and confusing names.
   - Look for over-long functions and inconsistent patterns between similar modules.
   - Simplify only where behaviour stays the same and tests prove it.
   - Keep each file's comment density and idioms.
5. Wording: check every user-facing string in the dashboard, landing, emails and errors, every doc
   and the README.
   - Each must be accurate against the code, consistent ("events", plan names, limits, retention),
     and follow technical-writing and unslop.
   - Pricing copy everywhere must match packages/core/src/plans.ts.
6. Landing and docs: run /seo-geo on apps/landing and apps/docs.
   - Cover titles and descriptions, headings, structured data, sitemap-docs.xml, llms.txt and
     llms-full.txt, Markdown copies of pages, internal links, AI crawler access and citability.
   - Fix what's in our code, with the docs build's link check passing.
   - Don't add competitor names outside the three allowed files.
